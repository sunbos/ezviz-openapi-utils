# EZVIZ Unified 基础架构设计

日期：2026-11-14。状态：基于旧版审查与用户委托作出的设计，已分阶段实现基础客户端和设备查询；实际进度及验证范围见[实施路线](../plans/2026-11-14-delivery-roadmap.md)。项目名为 EZVIZ Unified，发行包名为 `ezviz-unified`，Python 导入名为 `ezviz_unified`。名称注册及仓库迁移尚未执行。

依据：[旧版评估](../research/2026-11-14-legacy-assessment.md)、[平台调研](../research/2026-11-13-ezviz-api-survey.md)。

## 1. 目标与边界

产品定位：面向萤石国内与海外平台的第三方 Python SDK，提供统一调用体验、明确的支持范围和持续兼容性验证。Python 包是交付形式；SDK是对外产品；维护harness是独立运行的维护设施。当前不建设通用ADK。

选择 `ezviz-unified` 是因为它直接表达跨平台统一接入这一核心价值，便于开发者识别用途。`infra` 对部署和基础服务的预期过宽，`harness` 强调内部执行方式，均不作为总项目名。统一不代表所有地区具备相同权限或能力，支持范围由契约与验证记录明确表达。

提供可独立使用的 Python SDK，支持官方国内/海外接口的确定性调用、清晰的能力边界与可验证维护。官方特有功能允许保留独立入口，不强行压成最低公共能力。App API作为显式可选adapter，不自动接管官方认证失败。

首期实现足够小的真实闭环；完整接口目录可以逐步扩展，但不以自动生成的方法数量宣称可用覆盖。媒体解码、P2P、配网与对讲单列后续评估。

普通SDK调用不依赖LLM、任务调度器或维护服务。业务agent与维护agent使用SDK，但不成为安装核心包的必要依赖。

## 2. 技术选择

- Python最低版本采用3.12，以获得较长支持窗口，并便于未来评估要求3.12的App adapter。旧版最低3.8已结束官方支持。[Python版本状态](https://devguide.python.org/versions/)
- transport采用HTTPX，提供同步Client与AsyncClient，面向脚本和并发服务共用契约、编码及响应解析逻辑。使用requests本身不构成旧版缺陷；更换库的目的在于统一可注入边界、同步/异步支持、超时和生命周期。[HTTPX Clients](https://www.python-httpx.org/advanced/clients/)
- 核心类型先使用标准库dataclass/TypedDict与明确校验函数；不为每个上游字段引入复杂模型框架。响应保留raw字段，对新增字段前向兼容，关键必填字段缺失则报协议错误。
- 基础开发工具采用pytest、mypy、Ruff和构建安装验证；维护agent的模型和编排框架在维护实验阶段按需求选择，不作为SDK的依赖。

以上是设计选择，不是现有实现或性能结论。

## 3. 分层职责

| 层 | 职责 | 约束 |
| --- | --- | --- |
| 契约目录 | operation id、来源、区域、权限、参数位置、编码、响应规则、重试语义 | 对每项标记来源核实、离线验证、真实验证；未知不是支持 |
| Auth provider | appKey/appSecret、外部token、后续托管/子账户及App会话 | 认证主体分开，不把不同token类型混用 |
| Region resolver | 认证入口、业务域名、可信主机规则 | 海外缺路由信息要明确失败，禁止静默回国内 |
| Transport | 注入HTTP client、连接池、超时、关闭、网络异常转换 | 全部业务请求经唯一入口，公开可配置期限 |
| Codec与错误层 | form/query/header/JSON编码、平台/设备双层状态、原始错误码 | 按接口规则解析；异常与日志脱敏 |
| 业务API | devices、video、storage、events等按需增加 | 显式方法与稳定参数；特殊平台能力保留扩展入口 |
| 维护harness | 发现变化、产生候选改动、验证和提交结果 | 独立于运行SDK，不能自行降低验收标准 |

初期在一个仓库、一套核心发行包中组织模块。SDK由普通Python程序或现有agent框架调用；先验证SDK和维护闭环，不建设插件市场。

目录职责（以实际文件为准，skills仍待后续场景需要时引入）：

```text
src/ezviz_unified/   # 客户端、认证、区域、传输、业务域与打包的契约数据
tests/              # SDK离线回归、安装验证、显式启用的真实验收
harness/            # 上游变化检测、候选变更与受控维护流程
skills/             # 维护流程的可复用操作指南
evals/              # 维护任务评测、固定基线与独立验收
docs/               # 产品文档、来源证据、设计与迁移说明
```

SDK只打包运行所需模块与契约；维护调度、模型调用和评测工具由独立命令运行。契约元数据记录调用方式和证据，不能作为执行任意代码或扩大权限的入口。

## 3.1 独立产品与旧项目归档

新SDK使用独立发行名、导入名与API，不继承旧utils的兼容义务。旧版清单仅作历史调研；不作为新接口范围、CI输入或完成比例。现阶段复用Git开发分支不代表产品依赖旧项目。

新用户入口为 `ezviz-unified` / `ezviz_unified`。不提供旧导入路径、方法别名、兼容适配或默认行为保留。目标是将新代码、文档与CI迁入独立仓库并核验，再将旧仓库设为只读归档，保留旧版本与历史供查阅。

新仓库交接、旧仓库归档与PyPI首次发布属于后续交付步骤，本轮尚未执行这些外部变更。

## 4. 请求与认证生命周期

1. 构造客户端只校验配置，允许在首次请求前注入transport和token provider；不在构造函数中发起认证网络请求。
2. 以可注入时钟判断到期时间，预留刷新提前量；同一provider内合并并发刷新。持久缓存是可选接口，首期不要求Redis等外部服务。
3. 根据operation契约决定token位置，创建新的参数对象，避免修改调用者传入的字典。
4. 解析HTTP、平台与设备层结果，分别保留原始错误码和操作标识。网络超时、认证失败、权限不足、设备不支持、协议漂移使用明确异常类别。
5. token失效后可更新缓存，但是否重发原请求由operation策略决定。只读查询可以有限重试；写操作没有幂等或未执行证据时不自动重放。
6. 提供close/aclose与上下文管理；客户端输出、repr、异常、trace都经过脱敏。默认不记录视频链接和完整业务响应。

areaDomain只接受已验证的HTTPS主机规则；地区配置来源与最近核实时间进入契约目录。海外完整规则未补齐前，不把旧8区域表直接作为当前已验证配置。

## 5. 测试与eval从第一阶段建立

| 层级 | 验证内容 | 结果口径 |
| --- | --- | --- |
| 离线单元/契约 | token失效、超时、参数编码、多层错误、schema漂移、脱敏、路由 | 网络被阻断，使用可控时钟与假transport |
| 安装验证 | wheel安装后的公共导入、版本一致、类型标记 | 不从仓库src命名空间绕过分发验证 |
| 真实只读 | 国内及一个确认海外集群的认证、设备/通道、状态、录像/地址查询 | 按区域、账户和设备分别报告；缺条件为未验证 |
| 真实可逆写 | 明确选定设备的读取→修改→核验→恢复 | 独立启用、操作allowlist和恢复流程；不进入默认pytest |
| 维护eval | 新字段、破坏性参数变化、网页排版变化、文档矛盾 | 检查修复正确性、误改、回归、证据不足时停止发布 |

格式化、删除与固件升级等操作默认仅做请求契约验证。skip不能计作通过，未知API错误不能普遍转skip。不能用同一份候选schema同时生成实现和唯一验收依据；保留独立基线、人工核对样本与留出案例。

PR检查至少包括离线测试、安装验证、版本一致、类型/lint检查。发布需要这些检查通过；真实验证覆盖另列，不因离线检查全绿而宣称全部硬件支持。

## 6. 维护闭环与自我改进

先用确定性工具完成文档抓取、快照与hash、目录差异、契约校验、测试及结果存档；需要语义判断时再调用模型。每次候选变更必须绑定来源和原始证据，并形成可检查的diff。

流程：上游文档/SDK/运行反馈 → 变化分类 → 候选契约 → 候选代码 → 独立评测 → 符合预设策略的发布或待处理记录 → 监测与回退。

官网内容是数据来源，不能通过其中的指令改变执行权限或发布策略。维护agent先只产生候选改动；自动发布范围待真实表现稳定后逐项开放。后续RSI可优化skills、工具和执行策略，但受独立eval、预算、权限与回退约束；修改验收规则需独立审查。

## 7. 分阶段验收

1. **契约与安全基线**：按官方来源建立能力目录，明确地区、权限、未核实与暂缓原因。先补海外认证/区域证据，固定核心回归集。
2. **小内核**：实现auth、region、transport、错误与同步/异步入口；旧版8项复现对应需求全部得到正确处理。
3. **最小真实切片**：先实现token获取/更新、设备分页列表、单设备信息、设备通道列表和状态查询；补齐协议证据后，加入一个v3录像查询。国内与一个已确认海外集群分别验收，不能用国内成功代表海外支持；缺少区域账户或设备时明确保留未验证状态。
4. **维护实验**：注入新增字段、破坏性参数、纯网页变化；正确产生修复或保留旧版并报告证据缺口，旧回归不能退化。
5. **按证据扩展**：依据官方契约与用户场景逐域扩展；再评估App数据增量、业务skills和更高自动维护权限。

旧方法数量不进入验收目标，也不承诺无人维护。扩张依据是官方契约覆盖、实际业务验证、回归情况、人工介入次数和运行成本。
